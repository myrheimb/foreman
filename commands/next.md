---
description: Run the next task of the approved phase in a fresh context
argument-hint: [task number in the approved phase]
---

Load the `foreman:foreman` skill with the Skill tool and follow it. It holds the file formats and the rules.

1. Find the phase with status `approved` with `grep -l '^Status: approved' docs/plan/phases/*.md`. If there is none, tell the user to run `/foreman:plan` and stop.
2. Print its outline with `grep -n -E '^(## |### Task |- \[[ x]\] [0-9]+\.)' <phase file>`. Take task number $ARGUMENTS of that phase, or its first unticked task if no number was given. The number never names a phase. If every task is ticked, suggest `/foreman:close` and stop. Read only what this command needs: with the Read tool and the outline's line numbers, read the Milestone, this task, its log entry if it has one, and Decisions. Find the `Next needs` lines addressed to it with `grep -n 'Next needs (task <number>)' <phase file>`. Read the rest only when the user asks about it.
3. If this task is unticked and its log has a `Review failed:` line, its uncommitted changes are the earlier attempt: skip this step. Otherwise, if `git status` shows uncommitted changes outside `docs/plan/`, list the files and ask whether any are follow-up tweaks not yet logged. Log those as `Amended:` under their task. With `Commits: foreman`, commit the tweaks as the skill's Commits section says, and ask the user to commit the other files before the task starts. With `Commits: me`, ask the user to commit all of them before the task starts, unless Decisions record that they commit per phase.
4. If the task's log has an `Unverified:` line, do not hand it to a coder again. Ask the user for the result of those checks and go to the unverified case in step 6.
5. Hand the task to the `coder` agent as the path of the phase file and the task number, nothing more. Do not read the code yourself first. If you cannot start the `coder` agent, say so and stop. Do not do the task yourself. If the task has failed twice, counting its `Failed:` and `Review failed:` lines, first ask the user whether this coder should run on Opus, with the Agent tool's `model: opus`.
6. When it returns, add its log entry in the skill's format. A reply that does not follow the coder's format counts as blocked. If the coder took long, you cannot see why: say it may have waited on a permission prompt, and do not guess further.
   - Blocked: show the user what is in the way and the coder's recommendation, and ask them to decide. Record the answer under Decisions. If it changes what another task must do, rewrite that task and its "Done when" now, as rule 9 asks, instead of leaving it to a `Next needs` line. Then hand the same task to a new `coder`.
   - Unverified: leave the task unticked. Give the user the commands that did not run and ask for their exit codes. If all pass, continue as done. If one fails, log it as `Failed: <command>: <the key error line>`, ask the question rule 9 asks after a failure, and unless the user changes or closes the phase, hand the task to a new `coder`.
   - Done: hand the task to the `reviewer` agent as the path of the phase file, the task number and the coder's Verified lines. If you cannot start the `reviewer` agent, say so and stop, with the task unticked. If its reply does not follow the reviewer's format, start one new `reviewer`, and if that reply does not either, say so and stop.
   - Review failed: leave the task unticked. Log its must-fix findings in one `Review failed:` line. When the log already has one, replace it and count the failed reviews, as in `Review failed (2):`. Show the user the findings and suspicions. From the second failed review on, ask the question rule 9 asks after a failure. Then ask whether to send the task back to a coder. A finding the user rejects leaves the line and goes under Decisions with the reason. If none is left, continue as passed. On yes, hand the same task to a new `coder`, then its result to a new `reviewer`, as above.
   - Review passed: tick the task, delete the earlier `Next needs` lines addressed to this task that it handled, and delete its `Failed:` and `Review failed:` lines, putting what they said in the commit message instead. Add each "Untested until deploy" item and each "Needs a human look" item to the milestone's `After deploying` list unless it is already there. Tell the user the result in two lines, followed by each `Assumed:` choice and each "Needs a human look" item. Show the reviewer's minor findings and suspicions, and offer to add each to `BACKLOG.md`. Commit this task's files, the plan files it changed included, as its own commit, as the skill's Commits section says. With `Commits: me`, say to commit before the next `/foreman:next`, since step 3 stops on uncommitted changes. Do not re-run its checks unless a Verified line is doubtful: the reviewer and the milestone at `/foreman:close` are the independent checks, and re-running pulls build output into this session.
7. Do not start the following task. The user runs `/foreman:next` again.
